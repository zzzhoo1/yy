# 2026-08-23 — BitBetter 在无 Docker 沙箱中完整跑通

## 重大里程碑
在受限沙箱（无 CAP_SYS_ADMIN，Docker 无法跑容器）中，用 **crane + dotnet** 绕开 Docker，成功运行 Bitwarden Identity + API，并**完整跑通密码认证 token 流程（HTTP 200 JWT）**。

## 关键修复链（initdb 用户 seeding）
1. csproj 需引用 `Microsoft.Extensions.Options` 包
2. `PasswordHasher<T>` 无无参构造 → 需 `Options.Create<PasswordHasherOptions>()` 反射注入
3. `Kdf` 是枚举 `KdfType`，不能设 int 0 → 用 `Enum.Parse(KdfType,"PBKDF2_SHA256")`
4. User 实体用 **EF 模型** `Bit.Infrastructure.EntityFramework.Models.User`（非 Core.Entities.User）
5. `DbSet.AddAsync` 返回 `ValueTask<EntityEntry<T>>`（非 Task）→ 需 `AsTask()`；签名带 CancellationToken
6. `SaveChangesAsync` 只有带 CancellationToken 重载
7. User.ApiKey 是 NOT NULL → 必须设置
8. **DataProtection key ring 必须共享**：initdb 和 Identity 都要 `PersistKeysToFileSystem("/tmp/bw-data/dp-keys")` + `SetApplicationName("Bitwarden")`，否则解密失败
9. **MasterPassword 必须加 `"P|"` 前缀**（`Constants.DatabaseFieldProtectedPrefix = "P|"`）——DataProtectionConverter 以 P| 开头才解密，否则返回原值 → VerifyHashedPassword 报 Base64 错误

## token 请求必须带
- `Bitwarden-Client-Version: 2026.8.0` 头（否则 version_header_missing）
- `deviceType=9` + `deviceIdentifier=<GUID>` + `deviceName`（否则 device_error）

## 深入推进：完整用户生命周期跑通（全部 HTTP 200）
之前 API 路由 404 的根因是**路由前缀不是 `api`**——控制器注册在根路径（`/accounts/*`、`/sync`、`/plans`、`/version` 等），`/alive`、`/config` 用 `~` 前缀忽略全局。之前测试用 `/api/...` 所以 404。

### 关键路由发现（2026.8.0）
- API 控制器路由在**根路径**（无 `api` 前缀）：`/accounts/profile`、`/sync`、`/plans`、`/version`、`/devices`
- `InfoController` 用 `~/alive`、`~/now`、`~/version`（`~` 忽略全局前缀）
- **prelogin 在 Identity 服务**（非 API）：`POST /accounts/prelogin`（旧）和 `/accounts/prelogin/password`（新），返回 kdf 配置
- **注册是两阶段**：`POST /accounts/register/send-verification-email` → 返回 `BwRegistrationEmailVerificationToken_...` token → `POST /accounts/register/finish`

### 注册 finish 请求体关键字段（2026.8.0）
- 验证 token 字段名：**`emailVerificationToken`**（不是 `token`）
- 密钥对：`userAsymmetricKeys: {publicKey, encryptedPrivateKey}` 或 `accountKeys`
- 密码：`masterPasswordHash` 被 Identity 当密码校验，**必须 ≥12 字符**（`RequiredLength=12`）；注册和登录必须用同一个值
- 其他：`userSymmetricKey`（替代旧 `key`）、`kdf`、`kdfIterations`
- 成功响应：`{"object":"registerFinish"}` HTTP 200

### 完整生命周期验证成功
1. 注册：send-verification-email → 200 + token；register/finish → 200
2. 登录：password grant → 200 + JWT

### 踩坑：alice 登录失败（HTTP 500 key ring 不匹配）
原因：initdb 用 `BW_DATA_DIR=/tmp/bw-test-data`（dp-keys 在 bw-test-data/dp-keys），但 Identity 的 appsettings 固定 `dataProtection.directory=/tmp/bw-data/dp-keys` → key 不匹配。
**教训：initdb 的 BW_DATA_DIR 必须与 appsettings 的 dataProtection.directory 一致**（默认都是 /tmp/bw-data）。init-sandbox.sh 默认一致，正常。
另：curl 传密码用 `--data-urlencode "password=$PW"` 比内联 `password=xxx&` 更可靠（避免特殊字符/编码问题）。

### 密码哈希一致性确认
- `PasswordValidationConstants.PasswordHasherKdfIterations = 100000`，与 ASP.NET Identity `PasswordHasherOptions` 默认 IterationCount=100000 一致 → initdb 用默认 options 即可，无需特殊配置。

## GitHub Push Protection 拦截 + 解决（token 泄漏）
推送含 `.git-token.example`（内含真实 PAT `github_pat_...Skn7`）的 commit 时被拒：
`GH013: Repository rule violations - Push cannot contain secrets`。
GitHub 的 Push Protection 检测到 `github_pat_` 前缀的 token 出现在 commit 里，视为泄漏 secret，阻止 push。

### 解决
1. 把 `.git-token.example` 内容改为占位符 `<YOUR_PAT>`（不含真实 token）
2. 用 `git rebase -i` 把含 token 的 commit 标为 `edit`，amend 掉 token（filter-branch 的 index-filter 因 `$GIT_COMMIT` 展开问题没生效，改用 rebase）
3. 检查历史无 token 后 `git push --force`（历史被重写，需 force）

### 教训
- **不要在仓库文件里放真实 token**（即使叫 `.example`）。用占位符 `<YOUR_PAT>`。
- 真实 token 放 `/tmp/git-askpass.sh`（不在 git 里）即可。
- Push Protection 检查**所有 commit**，不只是最新，所以历史里的 secret 也要清。
- `git rebase -i` + `edit` + `amend` 比 filter-branch 更可靠地改写单个 commit 内容。
- 当前有效完整 token 在 `/tmp/git-askpass.sh`（`<YOUR_PAT>`），推送用 `https://x-access-token:<TOKEN>@github.com/zzzhoo1/yy.git`。
